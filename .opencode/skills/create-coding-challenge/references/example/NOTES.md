# Notes on the original example

The files in this folder (`assignment.md`, `utils.ts`, `main_test.ts`) are the
original example that inspired this skill. They are a **guide to the ideas**, not a
template to copy. Generated challenges follow `../challenge-format.md` and
`../test-runners.md`.

## Ideas to keep

- **Story first**: a short, realistic reason for the feature ("Support.ai needs
  a message parser for email and chat inputs").
- **One clear task**: "Complete the `parseCustomerMessage` function", with the
  input type and return type named exactly.
- **Numbered rules with exact values**: every output value is spelled out
  (`"email"`, `"chat"`, `"unknown"`, join with `\n`), so the tests can be
  predicted from the text alone.
- **An explicit fallback rule** ("Otherwise...") so edge behavior is defined, not
  guessed.
- **Starter code with only types and signature**: the learner writes the logic.
- **Tests map to rules**: each rule has a test case; each output field is
  checked separately with a strict comparison, so failures point at a single field.
- **Visible vs. extra tests**: the main paths are visible, and an edge case
  (non-string, non-array input) is checked separately. In the new skills, extra tests
  are generated only at review time and only for intermediate/advanced levels.
- **Readable test names** that include the input, and shared test data as named constants.
- **Light humor** in the test data, which keeps it engaging.
- **One concept per beginner challenge** (here, narrowing an `unknown` value).

## Things done differently in generated challenges

| Example | Generated challenges |
|---|---|
| Custom `./unit_test` harness (missing from the folder) with a `withSubmit` flag | The ecosystem's standard test runner (Vitest, pytest, go test, JUnit...) |
| Hidden cases live in the same test file | Hidden tests are generated by `review-coding-challenge` in a temp copy, never stored |
| `// ?` body, which does not compile in TypeScript | A single `Write your solution here` comment in the challenge's language, only in the files the learner edits, plus the minimal default return when needed to compile (for example `return 0;`) |
| Rules are numbered but have no IDs | Acceptance criteria with stable IDs (`AC1`...) used in tests, rubric and feedback |
| No guidance level | Guidance depends on difficulty (step-by-step, tips, or constraints only) |
| No run instructions or project config | `package.json`/`pyproject.toml`/... with a single setup and test command, plus a version pin file |
| No metadata | `.challenge/meta.json` and `.challenge/rubric.md` for the reviewer |
| Generic file names (`utils.ts`, `main_test.ts`) | Domain-specific names (`src/message-parser.ts`, `tests/message-parser.test.ts`) |
